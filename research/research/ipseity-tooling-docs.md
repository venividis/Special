## 0. The one thing to understand first

The repository is Foundry-shaped but **Foundry is never run**. `forge` was unreachable from the build environment (`tools/forge.mjs:5-8`: "Foundry's installer is unreachable from this environment, and so are GitHub, codeload and the crates.io API — there is no route to it"). Everything — compilation, the Solidity test suite, fuzzing, 22 adversarial verifiers, gas budgeting, deployment, deployment recovery — runs through Node on `@ethereumjs/vm` or over JSON-RPC. The CI workflow (`.github/workflows/ci.yml:40`) runs `npm run check`, which is the 26-step battery in `package.json:22`.

The second thing: every verifier here is written as an **attack**, not a demonstration, and each carries a narrative header recording the bug that motivated it. Those headers are the project's changelog; they are quoted below where load-bearing.

## 6. How the web UI is delivered, and how NFT ownership gates access

**Delivery — entirely from chain, two surfaces, no server or IPFS anywhere:**

1. *The instrument (per token).* `Ipseity.tokenURI(id)` → `Renderer` → JSON whose `animation_url` is `data:text/html;base64,…` of the whole WebGL2 app, stored as gzip bytes in SSTORE2 shards on `Engine` (`verify.mjs:95-118`), inflated in the browser by `DecompressionStream` from a loader that declares no globals (`verify.mjs:174-189`). Per-token state is injected by the contract as `window.IPSE={…}` between head and body (`verify.mjs:196-241`). The same document is served *un-wrapped* as HTML at `Premises.request(["token",id,"live"])` for 4.48M gas (`verify-premises.mjs:155-177`).
2. *The site.* `Premises` is an ERC-5219 router (`resolveMode()` = `"5219"`, `verify-site.mjs:388-402`) whose 23 page/desk addresses are immutable constructor arguments (`site.mjs:785-796`); each page renders HTML server-side in Solidity and emits a JSON config block of **on-chain-computed selectors** plus the client JS as Solidity string constants (`verify-site.mjs:627-691`; console JS/CSS live in `ConsoleCore`/`ConsoleSkin` SSTORE2 stores, `site.mjs:720-760`). A browser reaches it over `web3://<premises>:<chainId>/…` (ERC-4804/6860) or an HTTP gateway that is a pure `eth_call` relay (`gateway.mjs:120-130`, `portal.mjs:141-207`), or via ENS through the `contentcontract` text record (ERC-6821, `verify-site.mjs:2681-2688`). Every page contract has zero state-changing functions (`verify-site.mjs:3152-3184`).

**Ownership verification — a courtesy in the page, enforcement in the contracts:**

- The page connects a wallet (EIP-6963 discovery; the signing wallet is *chosen*, not raced — invariant 99), reads `balanceOf(wallet)` and walks `tokenOfOwnerByIndex` to learn what it holds (`README:209-215`, driven at `verify-site.mjs:1205-1225` where `IPT.mine()` and `body.held` come from those reads), and offers to act "as" one of those tokens. `/token/<id>/live` exists specifically because a `data:` frame has an opaque origin where no wallet injects (`verify-premises.mjs:155-161`).
- **The gate is not the access control.** README:217-221: "The gate in front of the composer is a courtesy, not a lock… there is no version of this where holding a token is what lets you *read*. What holding a token buys is the right to *write*, and that is enforced in a contract." Every write-side function checks the token, not the page: Parley's `mayActAs(id, who)` admits the owner and the token's ERC-6551 Reach only (invariant 79; `verify-parley.mjs:189-200`; live at `testnet.mjs:278-284` "the gate is the contract, not the page"); Pool/Lease/Succession/Consign use strict owner doors that exclude approved operators and renters (invariants 21, 70, 115); `lock`/`unlock` admit owner and Reach only (invariant 108); the Reach's `onlySigner` resolves `ownerOf` at call time so authority follows the token through a sale (`verify-vault.mjs:206-235`); session keys are stamped with the hub's transfer counter so a seller's key dies on sale (invariant 125).
- The console additionally refuses to build a transaction when the wallet's chain differs from the token's and names it in the crest (`verify-console.mjs:452-487`; INTERFACE.md:33-40).
- Standards used for identity: ERC-721 `ownerOf`/`balanceOf`/`tokenOfOwnerByIndex` (Enumerable), ERC-6551 (two accounts per token at two salts), ERC-4907 user (renter may operate, never speak/sell), ERC-5192/6454 lock, ERC-1271 attestations under the account's EIP-712 domain while sealed.

## 10. Unique ideas worth carrying into the merge

1. Verification as attack with narrated history: every verifier's header records the bug that created it, and the negative control that catches a harness lying (`forge.mjs:558-675`).
2. One deployment sequence for in-process and live chains (`Chain`/`RpcChain` twins) so "what the suite verified is what the testnet gets".
3. Recovery-by-walking-immutables with contradiction detection, held to the source by a test that is fed the historically broken table.
4. A build-failing `eth_call` gas-cap gate (50M floor, 10M warning) for a site that is only reachable through view calls.
5. The contract-emitted client is *executed* in CI against a DOM shim and the same EVM; selectors never computed in the browser; no float touches an amount.
6. Back-linked event logs read with single-block `eth_getLogs`; the walk's termination is a measured property.
7. Two ERC-6551 hands per token: a measured seal (balances before/after, deny-by-default on manifest assets) and a Grip whose guarantee is the absence of a function, asserted against the ABI.
8. Session keys bounded four ways, stamped with the transfer counter so they die on sale, with the cross-product documented rather than hidden.
9. Deployment records that every page address is spread into, reconciled from the chain, and a receipt journal that never holds keys.
10. The "read the real protocol ABI, not the mock's" lesson (`0x13137d65`), and the CREATE nonce-0 same-address-everywhere wiring with a dry run that proves it before spending.
